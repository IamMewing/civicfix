CivicFix — Code Tour & App Map

A guided walk through the finished codebase, in the order a real report actually flows through it — plus one habit worth carrying into your next build. Generated 2026-10-23, after Slice 11 (step-by-step filing instructions + real tutorial videos).

1The journey, as code

Four screens, three AI calls, one data file doing the heavy lifting. This is the order a photo actually travels through the app:

CaptureStep.tsx→ /api/classify→ /api/research→ /api/draft→ ReviewStep.tsx→ HandoffStep.tsx

2Stop by stop

UIsrc/components/CaptureStep.tsx

Owns the whole pipeline's state in one component rather than three separate stateless screens — phase switches between capture / review / handoff, so real results flow straight through without re-fetching anything.

Why it's built this way: a manual category override in Review has to re-trigger research and drafting for the corrected category (see handleCategoryOverride) — that only works cleanly when one component owns the whole chain.

APIsrc/app/api/classify/route.ts

Sends the photo (and description) to Groq's vision model. Returns a category, a confidence score, and — distinctly — an isCivicIssue boolean.

Why: confidence alone couldn't tell "ambiguous civic photo" apart from "not a civic photo at all" (a face, a pet). Splitting them stops the pipeline from quietly drafting a nonsense complaint for an irrelevant photo.

APIsrc/app/api/research/route.ts reads authorities.json

The project's actual unique kernel. Loads src/data/authorities.json (cached in memory per server process — restart after editing it), scopes to the reporter's city, and asks the model to pick the correct pre-verified entry — never to invent one.

Why: a safety net (matchedEntry) checks the model's chosen reportingChannel against the real entries it was offered, and builds the response from that verified entry, not the model's echoed JSON — so a model typo or omission can never corrupt the step list or drop a verified field. This is the single most important pattern in the codebase; see Section 3.

APIsrc/app/api/draft/route.ts

Takes the classified category, the research result, the description, and the location, and asks the model to write the actual complaint text.

UIsrc/components/ReviewStep.tsx

Every drafted field is a real editable input — nothing leaves the app without a chance to fix it, including a full category override.

UIsrc/components/HandoffStep.tsx

The actual proof-of-concept finish line: opens the real government portal in a new tab, with the complaint text ready to copy, plus (Slice 11) a numbered step list, a helpline, and a real tutorial video — all optional props, all sourced straight from the verified data, none generated on the fly.

DATAsrc/data/authorities.json

Every fact a reporter is ever shown about a government authority lives here, and nowhere else: national_fallback (CPGRAMS) plus cities.<slug>.{pothole,streetlight,water,general_fallback}, each with a URL, a cited sourceNote, and (as of Slice 11) live-verified filingSteps, helplinePhone, and tutorialVideoUrl.

Why: this file is what makes "never hallucinate a government source" enforceable in code rather than just a prompt instruction — see Section 3.

3Decisions worth remembering

Three choices in this codebase generalize well beyond this one project:

Verified data as source of truth, AI as a chooser, not a knower

The model never answers "who handles this?" from its own knowledge. It's handed a small, real, pre-verified slice of authorities.json and asked to pick from it. Hallucination risk drops from "the model might invent a government URL" to "the model might pick the wrong one of three real options" — and even that's caught by the safety net below.

Reconcile against source data, don't trust the model's echo

/api/research/route.ts asks the model to return five short fields, then — instead of using that JSON directly — finds the matching entry in the original verified data and builds the real response from that. Anything long, structured, or easy to garble in a retype (like filingSteps, an array of strings) flows through from the source, never from what the model typed back.

When a tool says "not found," try a different tool before concluding it's true

Plain web search returned zero real YouTube links across 10+ queries for Slice 11's tutorial videos. Navigating directly to youtube.com/results?search_query=... in a live browser found a real, relevant video on the first try, every time. The lesson wasn't "no videos exist" — it was "this search path doesn't reach them."

4A practice to reuse

Before trusting an AI-cited source, ask: can a human (or the agent itself) click through it live?

This project shipped twice with broken links its own research had confirmed "working" — a dead typo'd URL on GHMC's own FAQ page, a redirect that had since rotted on Chennai's site. Both were only caught by actually navigating the real site with a browser, not by re-checking that the URL returned 200 OK. Reachability and usability are different claims. The next time an agent (yours or Claude's) hands you a cited source for something that matters — a government portal, a docs page, an API endpoint — the cheap extra step is: open it for real, click one level deeper than the homepage, and see what a first-time user would actually hit. It catches a category of failure that automated fetching quietly can't.
